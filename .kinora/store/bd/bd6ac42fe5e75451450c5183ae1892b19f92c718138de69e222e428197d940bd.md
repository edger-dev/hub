# Spec — hub connections authenticate with per-peer Ed25519 keys

**Contract.** Every `NodeIngress`, `PeerIngress`, `SessionIngress`, and
`ConsumerApi` lane must authenticate before registration, topology or session
reads, subscriptions, publication, routing, or session messages whenever
authentication is configured. A peer authenticates with its own Ed25519 private
key; the hub trusts only configured public keys and permitted roles. This
includes the reverse `ConsumerApi` lane over a registered peer connection, which
authenticates in the opposite direction with the other hub's key.

For each lane the hub issues a random, single-use, short-lived nonce. The peer
signs the protocol version, hub name, service role, peer identity, key
fingerprint, and nonce. The proof names only the peer, key fingerprint, and
signature. Verification binds registration to that identity: a node cannot
register another node, a peer hub cannot take another peer's name, and a session
cannot claim another machine. A proof is valid only for its challenge and role.

Private keys are loaded from protected files and never logged or accepted as
command-line secrets. Public keys and role grants are declarative configuration.
Rotation may briefly trust two keys for one peer. Token authentication is an
explicit migration mode only: during rollout a hub may accept either token or
signature; after enrollment the token and its fallback are removed. With no
authentication configured, existing local behavior is unchanged.

**Transport boundary.** Signatures authenticate peers but do not encrypt
payloads. Remote deployment must use a private or separately encrypted network.
A signature without a fresh challenge is rejected as replayable, and first-seen
keys are not trusted on first use.

**Why.** A shared token cannot be revoked per machine and is exposed to every
peer. Per-peer signatures limit compromise, prove possession without sending the
private key, and bind topology and session identities to authenticated machines.

**Rejected.** Per-MCP-process identities, trust on first use, unsigned public-key
exchange, connector-only authentication, and treating signatures as encryption.

**Escape hatch.** A future channel-binding or TLS mechanism can replace the
handshake while preserving per-peer identities, role grants, and registration
checks.
