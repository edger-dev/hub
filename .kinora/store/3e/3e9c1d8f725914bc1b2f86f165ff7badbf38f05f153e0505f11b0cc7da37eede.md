# Spec — peer hubs dial over WebSocket with optional Cloudflare Access credentials

**Contract.** A peer address in `HUB_PEERS` may use `ws://` or `wss://` in
addition to a bare/TCP address. The peer dialer selects Vox's WebSocket link,
opens the same `ConsumerApi` lane, and uses the existing token authentication,
keepalive, and reconnect behavior. Topology and routing remain one hop. Peer
addresses remain explicitly configured on the dialing hub; authenticated
reverse discovery over that connection is defined by
kino://586748b7b572d2285f4747e555105426f76892c08966826018bfc00ae8d48efa.

**Cloudflare Access.** When `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`
are set, the WebSocket handshake carries `CF-Access-Client-Id` and
`CF-Access-Client-Secret`. Both must be nonempty and set together, and neither
is logged. They supplement `HUB_AUTH_TOKEN`. A direct VPS endpoint without
Cloudflare Access needs neither.

**Deployment.** Plain WS is for local/private endpoints; WSS is for public TLS
endpoints. A private hub can dial a public hub and register a reverse consumer
lane, so the public side needs no return route or Access credentials. Older
peers and existing mutual configurations retain their previous behavior.

**Why.** This removes the last TCP-only role without changing hub protocol or
state. Existing VPN-based peer links can migrate independently.

**Rejected.** Multi-hop routing, mandatory Access headers, and a separate
peer-only routing implementation.

**Escape hatch.** A later transport can replace WebSocket dialing without
changing the peer-registration contract.
