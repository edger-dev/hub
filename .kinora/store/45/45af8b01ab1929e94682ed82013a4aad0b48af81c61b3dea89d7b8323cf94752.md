# Spec — a routed call's error preserves which side failed

**Contract.** `ConsumerApi::route` returns `Result<RoutedReply, RouteError>`,
where `RouteError` distinguishes `Hub` (the hub could not deliver — no such
node/link, node offline) from `Node` (the call reached the connector and it
refused). The consumer can always tell delivery failure from connector rejection.

**Chosen.** A two-arm structured error that keeps the layer boundary. The arms
warrant different consumer reactions: a `Hub` failure often means the consumer's
topology is stale (refresh discovery, retry), while a `Node` failure means the
connector said no (surface it; do not blindly retry).

**Rejected.** Flattening a node-side `NodeError` into `HubError::Rejected(String)`
at the hub boundary. It is simpler but erases the hub-vs-node distinction and the
structured node detail, leaving the consumer to parse a string and unable to pick
the right recovery.

**Escape hatch.** Each arm wraps the existing `HubError` / `NodeError`, so those
can grow variants without touching `RouteError`; a consumer that does not care may
still treat any `Err` uniformly.
