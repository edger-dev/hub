# The Hub — a design-intent brief

*Consolidated from the kara prototype's spec ledger, as the hub stabilized. This
is intent + learnings for a clean-room rewrite, not code to port. It captures
**what was chosen, what was rejected, and why** — so a fresh implementation can
re-derive the design rather than inherit its accidents.*

Scope: the hub as **transport + topology + deployment**. The agent-first *job
substrate* and governed-command layer that ride on top are a separate brief — the
hub does not know about them; it only relays connectors.

---

## 1. What the hub is

The hub is the **stable boundary** of a small multi-machine mesh. Every other
component — the per-node daemons, the wrappers, the browser console — talks to the
hub and only the hub. Behind that boundary, implementation details (the event
store, the set of connectors, which node hosts what) can change without any client
noticing.

Three roles connect to it:

- **Nodes** — each machine runs one daemon that *reverse-dials* the hub and offers
  a set of **connectors** (process management, sessions, files, commands, …).
- **Consumers** — the browser console (a wasm SPA) and the agent's control shim,
  which open lanes *through* the hub to a chosen node's connectors.
- The hub itself owns nothing durable except **routing** and (optionally) an event
  store it mediates.

The single most important property: **the hub presents a stable protocol; what is
behind it is swappable.** Clients bind to the hub's protocol, never to a store API
or a node's local endpoint. This is the seam that lets everything else move.

---

## 2. The load-bearing decisions

### 2.1 Nodes reverse-dial and reconnect forever

Every node dials *out* to the hub and keeps retrying with backoff until the hub
answers. A node never listens for the hub to reach *in*.

**Consequence — a hub restart is a transient, not an outage.** This one property
pays for itself repeatedly:

- The hub host is allowed to **sleep**. An earlier design tried to defeat sleep
  (keep-awake daemons); that was over-cautious. A sleeping host is just another
  transient outage the mesh recovers from on wake.
- You can **restart the hub over a different channel** safely — nodes re-appear on
  their own. This is what makes self-restarting deploys possible at all (see §5).
- No inbound firewall/port-forward story per node — every node, including ones
  behind NAT/bridges, is a plain outbound dialer.

> **Learning.** "Reconnect forever" is not a resilience nicety bolted on late — it
> is the assumption the entire operational model leans on. Design it in first, and
> let *everything* (sleep, deploys, crashes) reduce to "the hub blinked."

### 2.2 Stable and dev are separate hubs on separate hosts

Two meshes: a **stable** mesh and a **dev** mesh, each with its *own* hub, on
*different* hosts.

- **Stable** hub: an always-on host, packaged as a service (§2.3).
- **Dev** hub: a plain dev process on the workstation, restarted at will.

**Rejected: one hub carrying both a "stable link" and a "dev link."** Dev churn —
a crashing hub, a bad rebuild, a wedged worktree — must never be able to touch the
stable mesh that the console and agents depend on; and stable must survive
uninterrupted dev iteration. Isolation by *host*, not by a link label inside one
process, is what actually guarantees that.

Because the two hubs live on different hosts, they **reuse the same port block**
with no collision — there is no dev-vs-stable port map to maintain.

**Escape hatch:** a solo setup collapses to one hub (dev == stable); reconnect and
routing behave identically with a single hub. Don't force two hubs on someone who
only has one machine.

> **Learning.** The instinct to put "stable" and "dev" as two links on one hub is
> a false economy — it saves a process but couples the two failure domains you most
> want isolated. Separate hosts is the cleaner boundary and removes a whole class of
> port-map bookkeeping.

### 2.3 The stable hub is a packaged OS service, not a dev binary

The stable hub is supervised as a **per-user OS service built from a pinned
package** (a launchd agent / systemd user service, chosen at build time by
platform) — never `build && ./target/debug/hub` in a terminal.

A dev binary dies with the shell, needs the repo + toolchain present, and isn't
restarted on crash or reboot. A packaged service is durable, restarts on crash,
survives reboot, and needs nothing but the artifact.

- **Rejected: a hand-written service manifest** — reuse the same cross-platform
  service module the node daemons already use; don't fork the pattern.
- **One host obligation** follows from putting it on a real machine: a **stable
  address**. A DHCP lease can move; use a fixed lease / VPN name / mesh gateway,
  not a bare ad-hoc IP.

The **dev** hub stays a plain dev process — only the *stable* hub graduates to a
service.

### 2.4 Nodes are hub-only — no local listener

A node daemon reaches consumers **only** as a hub provider. It dials the hub and
answers there; it does **not** bind a local listener. A hub is *required* — the
daemon errors at startup if none is configured. Symmetrically, the agent's control
shim is hub-only: it always targets a node *through* the hub (defaulting to the
local hub at 127.0.0.1), resolving the node down a ladder
(explicit → env → hostname).

Why remove the local direct path entirely:

- **Uniform addressing.** Every node is reached exactly one way — by its name in
  the hub's registry. No per-node local endpoints to discover, no ports to
  deconflict. Two daemons for one node are told apart by a **link label**
  (`stable` / `dev`), not by listen address.
- **It's the shape cross-node RPC needs.** "An agent on node A asks node B to run
  something" requires uniform hub-routed addressing; a local-only endpoint is the
  wrong shape.
- **Removes a footgun.** With no local listener, a second daemon for a node can't
  `EADDRINUSE`-crash-loop under the service manager — a duplicate degrades to
  harmless registration churn instead.

**Rejected: keep both** (local listener *and* hub). The local path existed only
for a co-located agent; that now goes through the local hub uniformly. Keeping it
is dead weight plus the crash-loop footgun. **Rejected: idle when no hub is set** —
a hard startup error is clearer; the hub is mandatory infrastructure now.

### 2.5 A node may run multiple links; the hub routes node→link

The local listener is gone, but the *link* concept stays: one machine may register
**more than one link for the same node** — e.g. a default **stable** link plus a
**session-scoped dev** link with its own toolchain environment. From the hub's
view it is **one node, many links**. A consumer request targets the node (plus an
optional link label); the hub routes to the selected link, defaulting to stable,
falling back to stable if the requested link is absent.

The subtlety worth preserving: **read/observe operations are link-agnostic** (any
link can service reads over shared node state), but **`start`-type operations care
which link** (the dev link carries the dev toolchain PATH; stable carries a minimal
one). Shareable, detached processes live in a shared per-node registry that both
links read freely and write to under a simple self-healing lock; non-shareable
processes (PTYs) belong to whichever link spawned them and die with it.

> **Learning.** "One node, many links" beat both "one link per node" (can't isolate
> dev churn from stable node infra) and "a distinct node *name* per link" (breaks
> shared node state). The right axis of variation was the *link*, under a stable
> *node* identity.

### 2.6 The hub exposes live node discovery

The console's node list is built from **live topology** — the hub reports which
nodes are currently connected — not a static list baked into the console. A static
list drifts: new nodes are invisible and a dead node looks alive. Discovery is
derived from the hub's existing reverse-dial registry, not a new registration
protocol. (Node auth / ACLs / offline inventory are explicitly out of scope until
needed.)

### 2.7 The hub mediates a swappable event store

Where the hub keeps an event log, clients still never touch the store directly —
they speak the hub protocol, and the store sits behind an `EventStore` trait
(`append`, `read_from`, live `tail`). A trivial file-backed impl proves the
protocol; a "real" impl drops in behind the same trait later. If the chosen store
engine is server-only (no embeddable library), the hub **owns it as a spawned
child** (start / health-check / restart) and speaks to it over localhost — and the
engine binary is built into the same package so the hub always has it to spawn.

> **Learning.** Routing every party through the hub protocol (never the store API)
> is what makes "switch the store later" a non-event. The trait is cheap insurance;
> pay for it up front.

## 3. The console is a direct hub consumer

The human web view is a wasm SPA that consumes the hub over WebSocket **directly**,
reaching every node's connectors and aggregating across nodes — there is **no
standalone HTTP/SSE bridge** in the middle.

- One console for all nodes; one consumer pattern (the same one the agent uses).
- The hub does the cross-host transport, so multi-host is *by construction*
  (per-node lanes), not a feature the console re-implements.
- No HTTP server in the daemon/core. The daemon is the link that exposes
  connectors; the console reads them over the hub. The core stays
  transport-agnostic — the connector is a thin adapter, not an HTTP surface.

**Rejected: a single-host HTTP+SSE host.** It was the right MVP for one machine but
cannot aggregate nodes; the hub already solves cross-host, so the bridge was
retired once multi-host became a requirement.

---

## 4. The console is served *by the hub host itself*

The stable console is a **pre-bundled static artifact** (a wasm build baked into
the package as a build output), served **in-process by the hub host** — no separate
web server (a reverse-proxy was tried and dropped). Browsing the hub host loads the
console **same-origin**, so it connects back to the hub with no manual `?hub=`
parameter.

This makes the console a durable artifact rather than a `serve`-style dev process
that dies with a shell. (The dev console stays a dev-server process against the dev
hub — same split as everywhere else.)

## 5. Deploying new hub/node code — and the fragility that taught the model

New code reaches a live node only after: push → bump the pinned package input →
run the per-host activation (which rebuilds the service from the new pin and
restarts it). The nodes reconnect afterward (§2.1), so the restart is a blink.

The **hard-won learning** is in how you *drive* that activation, because on the hub
host the activation **restarts the very supervisor issuing the command**:

- A **blocking** remote call that triggers the activation **loses its own
  transport** mid-restart and strands the handle. On the hub host this reads as a
  catastrophic failure when the deploy in fact succeeded.
- The fix is to run the activation as a **detached, file-backed job** that
  *survives the restart it triggers* and is re-adopted by the restarted daemon,
  then collect its result out-of-band once the connection returns. (This is the
  first place the job substrate — separate brief — earned its keep.)
- The expected terminal state of such a self-restarting job is
  **"outcome-unknown / killed-by-signal"** — and **that is success**: the daemon
  that owned the job restarted, so it *honestly* reports "I can't confirm the exit
  code" rather than losing the command. **Verify out of band** (the node answers a
  trivial command again; the hub host serves a freshly-hashed console bundle), not
  from the exit code.

Two supporting learnings from the same episode:

- **Order matters: switch the hub host *last*.** Switch leaf nodes first, the hub
  host last, so the hub is only interrupted once everything else is already on the
  new version and merely needs to reconnect.
- **A service manager kills the whole process tree by default.** A supervisor whose
  children are *meant* to outlive its restart must tell the service manager to
  signal *only the main process* (systemd `KillMode=process` / launchd
  `AbandonProcessGroup`), **and** the spawned child must not share a pipe with the
  supervisor (capture to files, not pipes) — otherwise the child dies of a broken
  pipe the instant it kills its parent-reader. Both vectors must be closed; closing
  one is not enough. (Detailed in the job-substrate brief.)

> **Learning.** The deploy is where a distributed design gets *tested*: the act of
> deploying is itself a cross-node, self-restarting operation. If your control
> plane can't survive restarting its own host, you find out here. Reverse-dial +
> reconnect + detached jobs are exactly what make it survivable — and "outcome
> unknown" being the *honest* success state is a design stance worth keeping, not a
> bug to paper over.

## 6. The minimal shape to re-derive at home

1. A hub with a stable, published protocol; nodes **reverse-dial + reconnect
   forever**; consumers open per-node connector lanes through it.
2. **Two hubs on two hosts** (stable service + dev process); collapse to one for a
   solo setup.
3. Stable hub = **packaged OS service** at a **stable address**; dev hub = plain
   process.
4. Nodes are **hub-only** (no local listener; hub required); **one node, many
   links** with node-level shared state and link-scoped `start`.
5. **Live node discovery** from the reverse-dial registry.
6. Console = **direct wasm hub consumer**, **served same-origin by the hub host**
   as a bundled artifact.
7. Store (if any) behind an **`EventStore` trait**, hub-mediated, engine spawned
   and packaged.
8. Deploy by **detached self-restarting jobs**, hub host **last**, verify
   **out-of-band**, and treat **"outcome-unknown" as success**.

Everything else — governed commands, the job model, the process manager — is an
*application* riding this hub, covered in the companion brief.
