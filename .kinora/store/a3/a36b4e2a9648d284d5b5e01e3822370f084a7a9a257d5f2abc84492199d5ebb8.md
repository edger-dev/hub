# Finding — a bare drop does not close a vox memory link

**Observed** (vox 0.10.0-rc.5, while building the node reconnect loop, M2 §2.1).

Dropping — or aborting the task holding — a peer's `ConnectionHandle` over
`vox::memory_link_pair` does **not** close the connection. The other side's
`ConnectionHandle::closed()` and the lane-level `caller.closed()` both hang, and
`caller.is_connected()` stays `true`.

**Why.** `establish_connection()` spawns driver tasks that own the link halves.
Dropping the returned handle does not stop those tasks, so nothing ever closes
the link. `ConnectionHandle::closed()` awaits the private control lane, which
never fires.

**What does work.** `ConnectionHandle::shutdown()` propagates: the peer's
`closed()` resolves promptly. Over a real transport a dying process sends
FIN/RST, which has the same effect — so production reconnect logic that waits on
`closed()` is correct.

**Impact.** Only on in-process tests: a fake peer must call `shutdown()`
explicitly rather than drop, or a reconnect test hangs. Cost us a debugging pass;
worth knowing before the hub's own tests are written.

**Open question.** Whether the hub should also call `shutdown()` on eviction, so
nodes learn of a deliberate disconnect promptly rather than via timeout.
