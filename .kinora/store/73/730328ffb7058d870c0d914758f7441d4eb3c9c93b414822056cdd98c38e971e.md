# Task — M4: run the mesh over real TCP

**Goal.** Take the M3 mesh out of the test harness: the hub **binds and accepts**
over TCP, the node **dials its configured hub address** and reconnects forever
against it, and both ship as runnable binaries. Success is two processes on a
real socket doing what the memory-link test proved.

**Realizes** (over a real transport; no new contract):

- kino://d661c899202c18f1d5a968f14d5c87a9d6b422aa62e450dd2134a1c1bfdec4cc —
  reverse-dial + reconnect forever, now against an address that can genuinely be
  down (§2.1).
- kino://bf406db5b660bd595cccdfcec5921121bb5a1ac9281a0d9a5c28be2d7ccc79b4 —
  the node's `HubEndpoint` becomes a dialled address, still hub-only (§2.4).

**Plan:** kino://25b4b31cc45a09329fefab41f607eac340c292e7deeb581f7054c6d2864522e8

**Done when:**

- The hub binds a TCP listener and serves every accepted connection
  concurrently; one node's disconnect never disturbs another's.
- The node dials its `HubEndpoint` over TCP and drives `reconnect::run` with a
  real dialer, so a hub that is down is retried, not fatal (§2.1).
- End-to-end over a real ephemeral TCP port: node registers, a consumer sees it
  in discovery, a routed call reaches it — and after the hub goes away and comes
  back, the node re-registers on its own.
- Both crates expose a runnable binary (`hub`, `node`) taking address/identity
  from CLI args or env.
- Zero warnings; committed; task + plan resolved.

**Out of scope:** TLS/WSS, the event store (§2.7), the console (§3–4), service
packaging and deploy (§2.3, §5), auth/ACLs, real connectors behind `deliver`.

---

**Resolved.** The hub binds and accepts over TCP; the node dials its configured
address and reconnects forever against it; both ship as binaries (`hub`,
`node`). Proven on a real socket (register → discovery → routed call) and, for
the reconnect contract, against a real hub **process** that is killed and
restarted — the node re-registers unaided. 49 tests green; clippy clean.

Learned: a vox connection cannot be made to "go away" from inside one process
(kino://0092dc47d183a6e1ec3e2185990f5e8904023dfe3e8057cc16b95fd7a6f33522), so
disconnect tests need a process boundary. Also, with the default backoff a node
may sleep several seconds after the hub returns before its next attempt — a slow
reconnect is not a failed one.

Carried forward: TLS/WSS, real connectors behind `deliver` (still stubbed),
consumer-side reconnect (only the node reconnects today), and graceful hub
shutdown signalling to peers.
