# Spec — live agent sessions exchange acknowledged messages

**Contract.** A session shim authenticates through `SessionIngress`, registers
its stable session id, node, harness, workspace, and optional context, and serves
`SessionService` on the same Vox connection. The hub keeps a live registry:
disconnect removes that connection's registration, and reconnect supersedes an
older one with generation-safe cleanup. One connection registers one session.
Several connections may carry the same logical session id when a harness runs
multiple MCP clients for one agent. The newest registration is the delivery and
sender identity target; if it disconnects, the newest surviving registration
becomes current. Listing exposes one entry per logical id.

Authenticated consumers can list live local sessions. `ConsumerApi` also
aggregates peer-local sessions, qualifying both session and node names as
`<peer>::<id>`. A send names a bare local session or one qualified peer session;
a still-qualified target after one hop is refused. Peer hubs use the same local
session operations, so no session is multi-hop or globally persisted.
A configured peer connection may use its proven key identity for forwarding
admission when a reverse registration is stale or unavailable. A shared token
does not prove a peer name and does not gain that fallback.

**Messages and identity.** A message carries an id, body, and sender session
metadata. Sender identity comes from the authenticated session registration,
never a claimed argument. Before forwarding to a peer, the origin hub qualifies
the sender with its own hub name; the receiving peer accepts that forwarded
identity only from the corresponding authenticated peer connection. A reply can
therefore name the original sender across the same peer relationship.

`SessionService.deliver` returns only after the receiving shim has accepted the
message into its local mailbox. An unknown, disconnected, or refusing target is
an error, never a delivered result. There is no offline queue or retained
history in the hub.

**Why.** Agents on connected nodes need live discovery and direct coordination
without pretending jobs and sessions are the same thing. Reverse registration
works through NAT and existing peer WSS links without a new public listener.
Harnesses may keep several MCP clients connected for one logical agent session;
this must not create ambiguous targets or make a duplicate disconnect terminate
the surviving session.

**Rejected.** Treating jobs as sessions, sender-supplied unauthenticated
identities, multi-hop forwarding, durable hub message storage, implicit terminal
input injection, and independent targets for every connection sharing one
logical session id.

**Escape hatch.** A later durable mailbox, singleton session broker, or
harness-specific immediate delivery adapter can sit behind the same acknowledged
`SessionService` boundary.
