# Spec — hub connections authenticate before use when a token is configured

**Contract.** When a hub has `HUB_AUTH_TOKEN` set, every `NodeIngress`,
`PeerIngress`, `SessionIngress`, and `ConsumerApi` connection must first
authenticate with that exact token. Missing or incorrect credentials are refused
before registration, topology or session reads, subscriptions, publication,
routing, or session messages. This includes the reverse `ConsumerApi` lane opened
back over a registered peer connection. `SessionService` is opened only by the
authenticated hub over the session's already authenticated connection. Successful
authentication is scoped to that connection. Nodes, peer hubs, sessions, and
consumers carry the token explicitly and never log it. With no token configured,
existing behavior is unchanged.

**Transport boundary.** The token authenticates a home-lab connection; it does
not encrypt it. Remote deployment must stay on a private or separately encrypted
network. The token is read from the environment, never a command-line argument.

**Why.** The remote inbox and live session messaging need authenticated delivery
without a new public service. Guarding the whole connection, including reads,
registration, and reverse peer lanes, avoids leaving topology, session, or event
data unauthenticated while only writes are protected.

**Rejected.** Connector-only credentials for this contract, authentication on
routed writes alone, mandatory tokens for existing local deployments, and
claiming the token makes a public plaintext listener safe.

**Escape hatch.** A future credential/TLS mechanism can replace the shared token
without changing the requirement that every operation is authorized.
