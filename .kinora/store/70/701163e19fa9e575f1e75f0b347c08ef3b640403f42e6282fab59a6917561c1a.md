# Spec — peer hubs register a reverse consumer lane

**Contract.** An explicitly configured outbound peer connection authenticates
and registers the dialing hub's own name through `PeerIngress`. The receiving
hub opens a `ConsumerApi` client back over that same Vox connection and exposes
the dialing hub's local nodes as `<registered-name>::<node>`. The dialing hub
also opens its existing forward `ConsumerApi` client under the configured
remote name. One authenticated connection therefore carries topology, events,
and routed calls in both directions; only the dialing side needs an address.

Both clients use `local_topology`, local event subscriptions, and `route` with
the peer qualifier stripped. Routing remains one hop. Topology is pulled from
the live peer rather than copied into registration. The dialing side owns
reconnect/backoff. A reconnect re-registers the same name and supersedes its
previous reverse client; connection generations ensure an older disconnect
cannot clear a newer registration. Existing mutually configured peers and
peers too old to support registration retain their forward-only behavior.

**Authentication and naming.** Registration and both consumer lanes require the
configured shared token before use. A registered name must be nonempty, contain
no peer separator, differ from the receiving hub's own name, and not replace a
configured peer. No unauthenticated public registration is allowed.

**Why.** Private hubs behind NAT or Cloudflare should be reachable from the hub
they dial, just as reverse-dialing nodes are, without return addresses or a
second connection.

**Rejected.** Multi-hop routing, pushed topology snapshots, a separate reverse
socket, and replacing a statically configured peer through registration.

**Escape hatch.** A later credential system can authorize peer names
individually without changing the reverse-lane transport.
