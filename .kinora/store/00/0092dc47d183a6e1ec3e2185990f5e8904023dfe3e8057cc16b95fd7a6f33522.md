# Finding — an in-process vox connection cannot be made to "go away"

**Observed** (vox 0.10.0-rc.5, building the hub's TCP transport in M4).

Over TCP, a peer's `ConnectionHandle::closed()` does **not** fire when the other
side is dropped *or* explicitly `shutdown()`-ed from within the same process —
confirmed with a minimal two-handle probe, no lanes involved. `shutdown()`
returns `Ok(())` and nothing happens.

The cause is the same one behind the memory-link finding
(kino://a36b4e2a9648d284d5b5e01e3822370f084a7a9a257d5f2abc84492199d5ebb8):
`establish_connection()` spawns driver tasks that own the socket halves. Neither
dropping the handle, aborting the task that awaits it, nor `shutdown()` stops
those drivers, so the socket is never closed and the peer sees no EOF.

**Production is fine.** When the hub *process* dies, the OS closes its sockets
and the node observes it immediately — verified by running the real binaries:
the node logs `hub connection closed; re-dialing` the moment the hub is killed.
The limitation is purely about simulating a disconnect inside one process.

**How to test a disconnect.** Run the peer being killed as a **separate
process** (`CARGO_BIN_EXE_<name>` makes this easy from an integration test) and
kill it; keep the other side in-process. That is what
`crates/hub/tests/restart.rs` does.

**Watch out for backoff when observing recovery.** With the default backoff
(250 ms → 30 s) a node that has been retrying for a while may sleep several
seconds *after* the hub returns before its next attempt. A short backoff in
tests keeps recovery observable; don't read a slow reconnect as a failed one.
